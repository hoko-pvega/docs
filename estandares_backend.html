1 Principios generales

  • Explícito antes que implícito. El nombre de una variable, función o clase debe decir qué hace, sin necesidad de leer su implementación.
  • Consistencia sobre preferencia personal. Si el manual dice cómo se hace, se hace así, aunque exista otra forma "igual de válida".
  • Nombre de clases, funciones y variables: Para el nombramiento se siguen las siguientes reglas:
    • Clases: Utilizar UpperCamelCase. Se define Usuario, CategoriaPermiso.
    • Variables y funciones: Utilizar SnakeCase. Por ejemplo id, user_name, get_fecha_cambio.
    • Constantes: Utilizar SnakeCase pero todo con mayúsculas. Por ejemplo CONSTANTE, VALOR_DEFECTO.
  • Todo el código nuevo se tipa. No se permite Any salvo excepción justificada y comentada.
  • Idioma: Los nombres se definen en dependencia de qué se está creando:
    • Variables y funciones: Inglés, salvo nombres de entidades/atributos que mantienen. (load_data, get_usuario, show_nombre).
    • Clases e interfaces: Español, respetando el nombre de tabla/columna que definida en base de datos. Se pueden utilizar palabras en Ingles en determinados casos específicos.
    • Comentarios y documentación: Español.
  • Imports: siempre absolutos desde app..., nunca relativos.
  • No lógica de negocio fuera del service: ni en router, ni en repo, ni en DTO.

2 Estándares de Documentación de Código

El objetivo de la documentación de código no es explicar qué hace cada línea, sino comunicar la intención y el propósito.

Para mantener una documentación útil y sostenible en el tiempo sin generar mantenimiento innecesario, la regla rectora del proyecto es la documentación basada en la reutilización. Es estrictamente obligatorio documentar toda clase, función o interfaz que esté diseñada para ser compartida y utilizada en múltiples partes del sistema.

2.1 Clases

Se describe la responsabilidad general de la clase.

class MiClase:
	"""
	Clase de ejemplo para escribir documentación.
	"""

2.2 Funciones

Se indican principalmente los parámetros que recibe y lo que retorna.

def get_comentarios_usuario(usuario_id: int, size: int=10) -> list[str]:

    Returns:
        Listado de comentarios.
    """
    return []

3 Tipado

  • Obligatorio tipar:
    • Parámetros de funciones.
    • Valores de retorno de funciones (no depender solo de inferencia en funciones públicas/exportadas).
    • Propiedades de clases e interfaces.
  • Prohibido:
    • Usar Any como salida fácil.
    • Tipos implícitos en funciones exportadas (aunque se infiera, se declaran explícitamente para que el tipado sea visible sin ir a la implementación).

4 Endpoints

4.1 Estructura de archivos

Cada endpoint vive en app/api/<entidad>/ con 5 archivos fijos:

NombreFunción
<entidad>_dto.pyDefine los data transfer objects para la comunicación con cliente.
<entidad>_filters.pyModelos para definición de filtros en endpoints de listado y paginado.
<entidad>_repo.pyRepositorio de la entidad para comunicación con base de datos.
<entidad>_svc.pyServicio de la entidad para enlace entre router y repositorio.
<entidad>_router.pyDefinición de endpoints.

No se debe mezclar responsabilidades entre archivos (p. ej. lógica de negocio dentro del router, o queries SQL dentro del service).

4.2 Data transfer objects (<entidad>_dto.py)

Importa siempre de app.shared.base_dto.

UsoNombreExtiende
Campos propios de la entidad (fuente única de verdad de los atributos)<Entidad>BaseBaseDTO
Respuesta genérica (incluye campos id y activo)<Entidad>DTO<Entidad>Base, BaseResponseDTO
Detalle completo (respuesta de GET /{id}<Entidad>SingleDTO<Entidad>DTO
Respuesta de listados (GET "", GET /pg)<Entidad>ListDTO<Entidad>DTO
Payload de POST<Entidad>CreateDTO<Entidad>Base
Payload de PUT (reemplazo total)<Entidad>UpdateDTO<Entidad>Base
Payload de PATCH, todos los campos opcionales<Entidad>PatchDTO

Reglas:

  • Los campos reales de la entidad se declaran una sola vez en {Entidad}Base. Las demás clases heredan, no redeclaran.
  • {Entidad}SingleDTO y {Entidad}ListDTO pueden estar vacías (...) si no agregan campos extra; existen para poder diferenciar el response_model de cada endpoint sin acoplar el schema de detalle al de listado.
  • PatchDTO nunca hereda de Base: se redeclara cada campo como opcional para evitar que un PUT/POST acepte campos parciales por accidente.
  • Tipos simples y explícitos (str, int, str | None), sin Any.

Ejemplo:

Entidad: sucursal
Archivo: sucursal_dto.py

from app.shared.base_dto import BaseDTO, BaseResponseDTO

class SucursalBase(BaseDTO):
    nombre: str
    area_id: int
    descripcion: str
    usuario_id: str

class SucursalDTO(SucursalBase, BaseResponseDTO):
    ...

class SucursalSingleDTO(SucursalDTO):
    area: str
    usuario_nombre: str
    usuario_apellido: str

class SucursalListDTO(SucursalDTO):
    area: str

class SucursalCreateDTO(SucursalBase):
		...

class SucursalUpdateDTO(SucursalBase):
    actualizar_datos: bool

class SucursalPatchDTO(BaseDTO):
    nombre: str | None
    area_id: int | None
    descripcion: str | None
    usuario_id: str | None
    cambio_estado: bool | None
    actualizar_datos: bool | None

4.3 Filtros (<entidad>_filters.py)


Importa de app.shared.base_dto (BaseFilters, BasePgFilters), fastapi.Query y typing.Annotated.

from typing import Annotated

from fastapi import Query

from app.shared.base_dto import BaseFilters, BasePgFilters

class {Entidad}Filters(BaseFilters):
    nombre: str # requerido/obligatorio
    descripcion: str = Query(None) # opcional que no puede ser null
    usuario_id: int | None = Query(None) # opcional que puede ser null


class {Entidad}PgFilters({Entidad}Filters, BasePgFilters): ...


ListFilters = Annotated[{Entidad}Filters, Query()]
PaginatedFilters = Annotated[{Entidad}PgFilters, Query()]

Reglas:

  • {Entidad}PgFilters no agrega campos propios: solo compone {Entidad}Filters + BasePgFilters (paginación).
  • Los alias ListFilters / PaginatedFilters son obligatorios y se usan tal cual en el router (no se referencia {Entidad}Filters directamente en las firmas de los endpoints).

4.4 Repositorios ({entidad}_repo.py)

Se pueden sobrescribir los métodos de base_repo (get, list_all, page_list, create, update, delete) cuando se necesita lógica adicional.

class {Entidad}Repository(BaseRepository[{Entidad}DB]):
    def __init__(self, session: Session):
        super().__init__({Entidad}DB, session)


def get_repository(session: DBSession) -> {Entidad}Repository:
    return {Entidad}Repository(session)

Reglas:

  • El repositorio no contiene lógica de negocio ni validaciones; solo acceso a datos. Si el CRUD estándar de BaseRepository no alcanza, se agregan métodos específicos aquí (no en el service).
  • {Entidad}DB (el modelo SQLModel) vive en app.core.models.{entidad}_db — nunca se define dentro del módulo api.
  • El factory get_repository es la única forma de instanciar el repo (para inyección de dependencias).

4.5 Servicios

Se pueden sobrescribir los métodos de base_service (get_by_id, list_all, page_list, create, update, patch, delete) cuando se necesita lógica adicional.

class {Entidad}Service(BaseService[{Entidad}DB, {Entidad}DTO, {Entidad}SingleDTO, {Entidad}ListDTO, {Entidad}Filters, {Entidad}PgFilters]):
    def __init__(self, repo: {Entidad}Repository):
        super().__init__(repo=repo, model={Entidad}DB, base_model={Entidad}DTO, single_model={Entidad}SingleDTO, list_model={Entidad}ListDTO)


def get_service(repo: Annotated[{Entidad}Repository, Depends(get_repository)]) -> {Entidad}Service:
    return {Entidad}Service(repo)


{Entidad}ServiceDependency = Annotated[{Entidad}Service, Depends(get_service)]

Reglas:

  • Aquí vive toda la lógica de negocio: validaciones, reglas de dominio y cambios necesarios al payload.
  • Los genéricos de BaseService deben pasarse en el mismo orden siempre: [DB, Base, DTO, ListDTO, Filters, PgFilters].
  • {Entidad}ServiceDependency es el único tipo que debe usarse en el router para inyectar el service (nunca Depends(get_service) inline en la firma).

4.6 Enrutadores

Endpoints estándar, en este orden y con esta forma exacta:

MétodoPathFunciónResponse modelNotas
GET""list_alllist[{Entidad}ListDTO]recibe ListFilters
GET"/pg"list_pgPaginatedResponseDTO[{Entidad}ListDTO]recibe PaginatedFilters
GET"/{id}”get{Entidad}SingleDTO
POST""create{Entidad}DTOstatus_code=201, pasa headers.user_id
PUT"/{id}”update{Entidad}DTO reemplazo total, pasa headers.user_id
PATCH"/{id}”patch{Entidad}DTO actualización parcial, pasa headers.user_id

Reglas:

  • Todo endpoint recibe service: {Entidad}ServiceDependency y headers: BaseHeadersDependency, en ese orden, como últimos parámetros después del payload/filtros propios del endpoint.
  • El router no contiene lógica: cada función es una línea que delega al service (return service.metodo(...)).
  • Los endpoints que mutan datos (create, update, patch) siempre propagan headers.user_id para trazabilidad de auditoría.
  • El nombre de la variable de ruta es siempre id (no puesto_id, no pk).
  • router = APIRouter(prefix="/...", tags=["..."]) con el prefijo y los tags especificados para no tener que definirlos en el archivo principal de importación de routers.

Mejoras que fáltan

Basado en el estándar completo que extraje del PDF (6 páginas, secciones 1 a 4.6) y en los patrones reales que encontré en el código durante la revisión anterior, esto es lo que el documento no cubre y debería agregar:

Carencias del documento

  1. Endpoints anidados/compuestos entre entidades
    El estándar solo define el CRUD de 6 endpoints de una sola entidad. No dice nada sobre endpoints como PUT /puesto/{id}/roles o PUT /rol/{id}/permisos, que viven en el router de una entidad pero delegan al service de otra. Sin esta regla, cada desarrollador decide distinto si eso es válido, en qué router va, o si el service propio debe envolver la llamada en vez de inyectar el service ajeno directamente.
    Dónde insertarlo: nueva subsección 4.7 Endpoints relacionales/compuestos, justo después de 4.6.
  1. Módulos que no siguen el patrón CRUD (casos especiales)
    No hay ninguna sección que contemple módulos como autenticación, SSE/eventos en tiempo real, o integraciones externas (LDAP) que legítimamente no necesitan los 5 archivos fijos. Hoy cada uno decide qué omitir sin criterio documentado, lo que genera módulos inconsistentes entre sí (permisos_usuario es un caso ambiguo: no está claro si su desviación es válida o no).
    Dónde insertarlo: nueva subsección 4.0 Excepciones a la estructura estándar, al inicio de la sección 4, antes de 4.1.
  1. Manejo de errores y excepciones de negocio
    El documento nunca menciona cómo debe lanzar errores un service (qué tipo de excepción usar, quién la captura, que el router nunca debe hacer try/except). Es una omisión grande para un estándar de backend, sobre todo porque la práctica actual sugiere que existe una jerarquía de excepciones.
    Dónde insertarlo: nueva subsección 4.5.1 Manejo de errores, dentro de "4.5 Servicios".
  1. Autorización por endpoint (permisos)
    No se explica cómo un endpoint declara qué permiso requiere, ni dónde se valida (dependency de FastAPI, decorador, chequeo manual en el service). Dado que el sistema tiene un registro de permisos, esta es una carencia crítica de seguridad, no solo de estilo.
    Dónde insertarlo: nueva sección 5. Autorización de endpoints, después de la sección 4 completa.
  1. Soft-delete (campo activo)
    El repositorio genérico hace soft-delete automático si el modelo tiene activo, pero el estándar no menciona este comportamiento en ningún lado, ni cuándo un modelo debe/no debe tener ese campo.
    Dónde insertarlo: dentro de 4.4 Repositorios, como regla adicional después de la ya existente sobre get_repository.
  1. Campos de auditoría (usuario_creacion_id, fechas, etc.)
    El estándar dice que create/update/patch "pasan headers.user_id" pero nunca explica el contrato completo: qué campos se estampan, en qué evento, y quién es responsable de hacerlo (¿service o repo?).
    Dónde insertarlo: dentro de 4.5 Servicios, junto a la regla de headers.user_id.
  1. Campos derivados/calculados en SingleDTO/ListDTO
    El ejemplo de SucursalSingleDTO muestra campos como area, usuario_nombre, usuario_apellido que no están en el modelo ORM base, pero no se explica de dónde deben salir (¿join en el repo? ¿cálculo en el service?). Sin esta regla, cada entidad resuelve esos campos de forma distinta.
    Dónde insertarlo: dentro de 4.2 Data transfer objects, como regla nueva después de las ya listadas.
  1. Validación de formato vs. reglas de negocio
    No queda claro si validaciones de formato (email, longitud, regex) deben ir como field_validator de Pydantic en el DTO, o si toda validación —formato incluido— va al service. Es una zona gris entre "4.2 DTOs" y "el service tiene toda la lógica de negocio" (regla 1).
    Dónde insertarlo: aclaración dentro de 1. Principios generales, junto a la regla "no lógica de negocio fuera del service".
  1. Constantes y catálogos compartidos (registries)
    El documento dice "constantes SNAKE_CASE mayúsculas" a nivel general, pero no dice nada sobre módulos tipo registry compartidos entre archivos (como listados de IDs o de permisos): dónde deben vivir, si son append-only, si se permite renumerar. Esto explica el bug real que encontré en lista_ids_menu.py (constantes en minúscula).
    Dónde insertarlo: nueva subsección al final de 1. Principios generales.
  1. Convención async/sync
    No se especifica si los métodos de repo/service/router deben ser async def o síncronos, ni el criterio para elegir uno u otro (por ejemplo, en generadores para SSE).
    Dónde insertarlo: dentro de 3. Tipado, o como nueva regla en "1. Principios generales".
  1. Testing
    No existe ninguna mención a pruebas: ubicación, naming, qué se debe cubrir por capa. Para un documento de "estándares de desarrollo Backend" es una ausencia notable, más aún porque el proyecto ya tiene pytest/pytest-asyncio instalados sin usar.
    Dónde insertarlo: nueva sección 6. Testing, al final del documento.
  1. Archivos auxiliares dentro de un módulo de entidad
    La sección 4.1 fija 5 archivos por entidad, pero no dice cuándo es válido agregar un archivo extra dentro de ese mismo módulo (como pasa hoy con menu_tree.py, lista_ids_menu.py, registro_conexiones.py) ni cómo debe nombrarse.
    Dónde insertarlo: como regla adicional dentro de 4.1 Estructura de archivos.

Nota aparte (no es una carencia, es una contradicción): el documento exige router = APIRouter() sin prefix/tags en 4.6, pero el código completo del proyecto hace lo contrario de forma consistente y deliberada. Esto no falta en el documento — está escrito, pero no coincide con la realidad. Conviene resolverlo junto con las carencias de arriba (actualizando el punto 4.6 o migrando el código), no agregarlo como si fuera nuevo.
