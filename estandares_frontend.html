1 Principios generales

  • Explícito antes que implícito. El nombre de una variable, función o clase debe decir qué hace, sin necesidad de leer su implementación.
  • Consistencia sobre preferencia personal. Si el manual dice cómo se hace, se hace así, aunque exista otra forma "igual de válida".
  • Finalización con punto y coma: Todas las líneas de código se tiene que finalizar con punto y coma (;).
  • Nombre de clases, funciones y variables: Para el nombramiento se siguen las siguientes reglas:
    • Clases: Utilizar UpperCamelCase. Se define Usuario, CategoriaPermiso.
    • Variables y funciones: Utilizar CamelCase. Por ejemplo id, userName, getFechaCambio.
  • Todo el código nuevo se tipa. No se permite any salvo excepción justificada y comentada.
  • Idioma: Los nombres se definen en dependencia de qué se está creando:
    • Variables y funciones: Inglés, salvo nombres de entidades/atributos que mantienen. (loadData, getSucursal, showNombre).
    • Clases e interfaces: Español, respetando el nombre de tabla/columna que define el backend. Se pueden utilizar palabras en Ingles en determinados casos específicos.
    • Comentarios y documentación: Español.

2 Estándares de Documentación de Código

El objetivo de la documentación de código no es explicar qué hace cada línea, sino comunicar la intención y el propósito.

Para mantener una documentación útil y sostenible en el tiempo sin generar mantenimiento innecesario, la regla rectora del proyecto es la documentación basada en la reutilización. Es estrictamente obligatorio documentar toda clase, función, variable, interfaz o constante que esté diseñada para ser compartida y utilizada en múltiples partes del sistema.

2.1 Clases

Se describe la responsabilidad general de la clase.

/**
* Clase de ejemplo para escribir documentación.
*/
class MiClase {
	...
}

2.2 Funciones

Se brinda una breve descripción y se indican principalmente los parámetros que recibe (@param) y lo que retorna (@returns).

/**
* Desripción de corta del proposito de la función.
* @param usuarioId - Id del usuario creador de los comentarios.
* @param size - Número de comentarios que se quieren obtener.
* @returns Listado de comentarios.
*/
getComentariosUsuario(usuarioId: number, size: number=10): string[] {
	return [];
}

2.3 Variables y constantes

Se define el propósito de la variable/constante.

/**
* Limite de tiempo para cierre de registros.
*/
limiteTiempo: number = 45;

3 Tipado

  • Obligatorio tipar:
    • Parámetros de funciones.
    • Valores de retorno de funciones (no depender solo de inferencia en funciones públicas/exportadas).
    • Propiedades de clases e interfaces.
  • Prohibido:
    • Usar any como salida fácil.
    • Tipos implícitos en funciones exportadas (aunque TypeScript los infiera, se declaran explícitamente para que el tipado sea visible sin ir a la implementación).

4 Definición de Data Transfer Objects (DTO)

Todo DTO que representa una entidad de base de datos debe de tener su propio archivo para definir interfaces. El nombre del archivo tiene el siguiente formato <nombre-entidad>.model.ts y se establecen en la siguiente ruta: src/app/shared/models/<modulo>/

4.1 Interfaz base

Todo DTO que representa una entidad de base de datos define su propia interfaz Base que agrupa los campos comunes y es extendida por las otras interfaces.

4.2 Tipos de DTO por entidad

Cada entidad tiene variantes, según el uso y extienden de la primera interfaz Base.

UsoNombreExtiende
Campos propios de la entidad<Entidad>Base
Respuesta genérica para POST, PUT, PATCH<Entidad>DTO<Entidad>Base (agregar id)
Detalle completo (detail)<Entidad>SingleDTO<Entidad>DTO
Listado (tablas, selects)<Entidad>ListDTO<Entidad>DTO
Creación<Entidad>CreateDTO<Entidad>Base
Edición (PUT: Si es necesario)<Entidad>UpdateDTO<Entidad>Base

Ejemplo con entidad sucursal: Nombre del archivo sucursal.model.ts

interface SucursalBase {
	nombre: string;
	direccion: string;
	telefono: string;
	categoriaId: number;
}

export interface SucursalDTO extends SucursalBase  {
	id: number;
}

export interface SucursalSingleDTO extends SucursalDTO {
	categoria: string;
}

export interface SucursalListDTO extends SucursalDTO {
	// puede estar vacío si no necesita campos adicionales
}

export interface SucursalCreateDTO extends SucursalBase  {
	fechaVencimiento: string;
	cambioEstado: boolean;
}

export interface SucursalUpdateDTO extends SucursalBase  {
	// solo se crea si la actualización necesita campos diferentes/adicionales
	// a la creación
	fechaVencimiento: string;
	cambioEstado: boolean;
}

Reglas:

  • Siempre <Entidad>ListDTO intenta mantenerse lo más básico posible.
  • Los modelos aquí descritos nunca deben de tener objetos/arrays como para de sus propiedades. Cuando son necesarios se deben de crear nuevas interfaces con esas llaves.

4.3 Ubicación de modelos

Todos los DTOs de una entidad viven en un único archivo: <entidad>.model.ts y no en archivos por variantes.

No se deben de crear DTOs ajenos a la entidad en el archivo. De ser sumamente necesario se deberán de importar de archivos externos.

5 Componentes

5.1 Convención de nombres

  • El nombre de la entidad siempre va en singular, sin importar el tipo de componente: Sucursal, nunca Sucursales
  • Sufijo según el tipo
    TipoClaseArchivo
    Listado<Entidad>List<entidad>-list.ts
    Formulario<Entidad>Form<entidad>-form.ts
    Detalle<Entidad>Detail<entidad>-detail.ts
  • Un mismo Form se utiliza tanto para crear como para editar, no se crean componentes separados Create/Edit.

5.2 Orden general de variables y funciones

Dentro de la clase de un componente de Angular, se utiliza el siguiente orden para definición de variables y funciones de forma genérica:

  1. Inyecciones: servicios y variables con inject().
    • El nombre de los servicios inyectados sigue el patron private <entidad>Svc = inject(<Servicio>);
  1. ViewChilds: variables viewchild<type>() y viewChildren<type>(). Siempre que se pueda se debe agregar la opción requerida si el html referenciado es estático: viewchild.required<type>().
  1. Inputs: variables input<type>(default). Tomar en cuenta cuando el valor no se define por defecto y la variable es requerida para obligar a las implementaciones a definirlo: input.required<type>().
  1. Outputs: variables output<type>().
  1. Iconos: lista de íconos utilizados en el HTML que son importados de FontAwesome.
  1. Variables de configuración de HTML: Listas y objetos de configuración de componentes referenciados y HTML en general.
  1. Variables en general seguidas de listas: Siempre primero declarar title seguido de variables y por último todas las listas necesarias. Utilizar signal siempre que la variable se utiliza en html y sufre cambios a lo largo del ciclo de vida del componente.
  1. Funciones de lifecycle de Angular: Iniciando por el constructor si existe (solo crearlo cuando es estrictamente necesario).

Ejemplo

@Component({
  selector: 'app-component',
  templateUrl: './component.html',
  styles: ``,
})
export class Component extends BaseList<UsuarioListDTO> implements OnInit {

	// 1. Inyecciones
  private usuariosSvc = inject(UsuarioService);
  private router = inject(Router);

  // 2. ViewChilds
  detalle = viewchild<Detalle>('detalle'); // elemento dinámico
  modal = viewchild.required<Modal>('modal'); // elemento estático

  // 3. Inputs
  idPersona = input<number>(); // input opcional indefinido
  idGrupo = input<number>(1); // input opcional con valor por defecto
  showDetalle = input.required<boolean>(); // input requerido

  // 4. Outputs
  save = output<boolean>()

  // 5. Iconos
  faPencil = faPencil;
  faTrash = faTrash;

  // 6. Variables de configuración de componentes HTML
  filters: Filter[] = [
    { type: 'text', label: 'Nombre', param: 'nombre', value: null, required: false },
    { type: 'text', label: 'Direccion', param: 'telefono', value: null, required: false },
    { type: 'text', label: 'telefono', param: 'direccion', value: null, required: false },
  ];

  // 7. Variables en general seguidas de listas (title primero)
  title = signal<string>('Listado de Usuarios');
  loading = signal<boolean>(false);
  usuarioList: signal<UsuarioListDTO[]>([]);
  opcionList: signal<OpcionListDTO[]>([]);

  // 8. Funciones de lifecycle de Angular
  ngOnInit(): void {
		this.usuariosSvc.getList().subscribe(res => {
      this.usuarioList.set(res);
    });
  }
}

5.3 Componentes de listado

Herencia

Todo <Entidad>Listextiende BaseList<TListDTO>, que resuelve variables y funciones comunes de listado:

  • Inyección de dependencias comunes:toastSvc, router, route, destroyRef
  • Variables
    • title: Titulo de la página
    • paginated: Signal con los datos paginados
    • isLoadingData: Signal para control de estado de carga
  • Funciones
    • getPaginated(): Función abstracta para obligar a definir en componente la llamada de información.
    • subscribeRouterEvents(): Función para subscribirse a los eventos de rutas y controlar filtros de paginado.

Cada componente concreto solo implementa getPaginated para hacer la llamada a su servicio y dar valor a su paginado.

Orden de variables y funciones

Los listados agregan variables y funciones comunes que se insertan dentro del orden general:

  1. getPaginated(): Primera función a continuación de las funciones del lifecycle de Angular.
  1. optionsHandler(): A continuación de getPaginated para manejar opciones de tabla. Solo se define cuando es necesaria.

Ejemplo

ngOnInit(): void { }

getPaginated(): void {
	... // obtención de datos para paginado
}

optionsHandler(): void {
	... // manejo de eventos de tabla
}

getPaginated

Debería de iniciar siempre con el cambio de la variable isLoadingData a true para mostrar la animación de carga de la tabla.

getPaginated(): void {
	this.isLoadingData.set(true);
}

5.4 Componentes de formulario

Herencia

Todo <Entidad>Form extiende BaseForm, que resuelve:

  • Inyección de dependencias comunes: toastSvc.
  • Variables
    • form: Formulario reactivo (abstracto)
  • Funciones
    • onSubmit: Función abstracta para obligar a definir en componente para llamar al finalizar el formulario.
    • isValidSubmit: Función para validar un formulario y marcarlo automáticamente como “touched”. Esta función deshabilita el formulario si es válido para protegerlo de ediciones.
    • resetForm: Función para resetear un formulario completo.
    • printForm: Función para imprimir todo el formulario.
    • printFormValue: Función para imprimir el valor del formulario

Cada componente concreto define su propio form con los campos de la entidad y onSubmit con lógica particular de guardado (llamadas al servicio), reutilizando el manejo de modo/validaciones de la base.

Orden de variables y funciones

Los formularios agregan algunas variables y funciones comunes que se insertan dentro del orden general:

  1. form: A continuación de las variables y listas generales y antes de las funciones del lifecycle de Angular.
  1. onSubmit(): Se define la función siempre a continuación de las funciones del lifecycle de Angular. Siempre

Ejemplo

... // variables y listas

form = new FormGroup({
	nombre: new FormControl<string>('', 
});

ngOnInit(): void {}

onSubmit(): void {
	if (!this.isValidSubmit()) return; // Validar siempre en primera linea
	...
}

onSubmit

La función onSubmit siempre (a excepción de casos específicos) inicia con la validación del formulario, haciendo un llamado a isValidSubmit que devuelve true si el formulario es valido y que se encarga de hacer el bloqueo de todos los controles para proteger de ediciones durante la ejecución.

Es importante que en el caso de falla del almacenamiento de los datos se vuelva a habilitar el formulario.

Ejemplo

onSubmit(): void {
	if (!this.isValidSubmit()) return; // valida y bloquea si los datos son válidos
	this.baseSvc.post(this.form.getRawValue()).subscribe({
		next: (res) => {
			...
		}, error: (err) => {
			this.form.enable({ emitEvent: false }); // se habilita el formulario
		}
	}
}

6 Servicios

6.1 Convención de nombres

  • Clase: <Entidad>Service (ej. SucursalService).
  • Archivo: <entidad>.service.ts (ej. sucursal.service.ts).
  • Un servicio por entidad. No se agrupan varias entidades en un mismo servicio, aunque estén relacionadas (ej. Sucursal y SucursalHorario van en servicios separados).

6.2 Herencia de servicio base

Todo <Entidad>Service extiende BaseService<TDTO, TSingleDTO, TListDTO, TCreateDTO, TUpdateDTO>, que centraliza las operaciones CRUD estándar sobre el endpoint REST de la entidad.

La clase BaseService provee los siguientes recursos:

  • Dependencias: cliente http de Angular.
  • Variables
    • baseUrl: valor base de la url (http://www.prueba.com/)
    • service: Nombre del microservicio al que se dirige
    • endpoint: Nombre del endpoint dentro del microservicio
  • Funciones
    • get: Llamada de una entidad por id.
    • getList: Llamada al endpoint para listado de entidades.
    • getPaginate: Llamada al endpoint paginado.
    • post: Para crear entidades.
    • put: Para edición general de entidades.
    • patch: Para edición por partes de entidades.
    • delete: Para llamada a eliminación de entidades (soft-delete).

Ejemplo de servicio implementado:

@Injectable({
  providedIn: 'root',
})
export class AreaService extends BaseService<AreaDTO, AreaSingleDTO, AreaListDTO, AreaCreateDTO, AreaUpdateDTO> {
  protected service = servicesPaths.configuraciones;
  protected endpoint = 'areas';
}

Regla clave: si una entidad necesita una operación fuera del CRUD estándar (ej. activar, exportarExcel, asignarUsuario), se agrega como método adicional en el servicio concreto, nunca modificando BaseService para casos particulares de una sola entidad.
